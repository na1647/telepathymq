Creating a Communication Node with new TelepathyMQ(identity)

TelepathyMQ allows independent communication nodes to be created so they can exchange events and execute asynchronous operations over a network.

The new TelepathyMQ(identity) constructor creates a new TelepathyMQ instance and assigns it a unique identity within the communication architecture.

Each instance represents a node capable of:

- Establishing connections with remote nodes.
- Accepting incoming connections.
- Sending and receiving events.
- Executing remote operations using defer().
- Listening for connection and disconnection events.
- Managing multiple connections simultaneously.
- Closing the connections it has created.

The identity assigned to each instance allows other nodes to identify it and communicate with it.

1. Overview

A TelepathyMQ node is created using the following constructor:

```javascript
const TelepathyMQ = require('telepathymq');

const node = new TelepathyMQ('server');
```

In this example:

- TelepathyMQ represents the library constructor.
- server is the identity assigned to the new node.
- node represents the created instance.

Once the instance has been created, it can be configured to accept incoming connections or establish connections with other nodes.

Creating an instance does not automatically start a server or establish any network connections.

These operations must be explicitly performed using the listen() and register() methods.

2. Constructor signature

**Signature**

```javascript
new TelepathyMQ(identity, debugFunction)
```

**Parameter**	**Type**	**Description**
identity	String	Identity assigned to the TelepathyMQ node
debugFunction	Function	Optional function used to handle debugging information

The first parameter is required.

The second parameter is optional.

**identity**

The identity represents the name under which the node is known within the TelepathyMQ network.

It is notably used to identify destinations when calling emit() and defer().

**Example**

```javascript
const server = new TelepathyMQ('server');
const client = new TelepathyMQ('client');
```

The two instances have distinct identities:

- server
- client

The client can subsequently communicate with the server using its identity.

```javascript
client.emit('server', 'message', {
  text: 'Hello from client'
});
```

**debugFunction**

The second parameter allows a custom debugging function to be provided.

This function is stored in the internal this.debug property and passed to sockets created by the instance.

If no function is provided, TelepathyMQ uses an empty function.

```javascript
this.debug = debugFunction || (() => {});
```

This allows debugging output to be disabled by default or replaced with a custom logging mechanism.

3. Instance initialization

When an instance is created, the constructor initializes several internal properties required by TelepathyMQ.

Here is the constructor implementation:

```javascript
class Telepathymq extends EventEmitter {

  constructor(identity, debugFunction) {
    super();

    this.identity = identity;
    this.relations = {};
    this.debug = debugFunction || (() => {});
    this.defers = {};
    this.socks = [];
  }

}
```

Each property has a specific purpose.

**Property**	**Type**	**Description**
identity	String	Node identity
relations	Object	Contains relationships with remote nodes
debug	Function	Debugging function
defers	Object	Stores pending deferred operations
socks	Array	Contains sockets managed by the instance

The constructor also calls super() to initialize the parent EventEmitter class.

This allows every TelepathyMQ instance to benefit from Node.js native event management capabilities.

4. EventEmitter inheritance

TelepathyMQ extends the native Node.js EventEmitter class.

```javascript
const { EventEmitter } = require('node:events');

class Telepathymq extends EventEmitter {
  constructor(identity, debugFunction) {
    super();

    // Initialization
  }
}
```

This inheritance allows each instance to use the native event management features.

Available methods include:

- on(): listen for an event.
- once(): listen for an event only once.
- off(): remove an event listener.
- addListener(): add an event listener.
- removeListener(): remove a specific event listener.
- removeAllListeners(): remove all event listeners.

**Example**

```javascript
const node = new TelepathyMQ('server');

node.on('register', identity => {
  console.log('Remote node registered:', identity);
});

node.on('unregister', identity => {
  console.log('Remote node disconnected:', identity);
});
```

These listeners allow applications to react to events generated by TelepathyMQ's internal operations.

**Important**

TelepathyMQ also overrides the public emit() method to support sending events to remote nodes.

There is therefore a distinction between listening for events using on() and emitting events using emit().

5. Assigning a node identity

Every TelepathyMQ instance has an identity defined when it is created.

This identity is used by other nodes to identify the destination of their communications.

**Example**

```javascript
const server = new TelepathyMQ('server');
const client = new TelepathyMQ('client');
const worker = new TelepathyMQ('worker');
```

In this example, three independent nodes are created.

Each instance has its own identity.

The client can then send an event to the server:

```javascript
client.emit('server', 'message', {
  text: 'Hello server'
});
```

The server can also send an event to the worker, provided that a relationship with that node has been established.

```javascript
server.emit('worker', 'task', {
  action: 'process'
});
```

The identity is therefore a central element of TelepathyMQ's communication mechanism.

Note

The constructor directly stores the provided value in this.identity. It does not explicitly validate its type, format, or uniqueness.

6. Debugging function

The constructor accepts an optional function that allows debugging information to be handled in a customized way.

This function is stored in this.debug.

**Example with a custom function**

```javascript
const TelepathyMQ = require('telepathymq');

const debug = (level, message) => {
  console.log(`[${level}] ${message}`);
};

const node = new TelepathyMQ('server', debug);
```

The debugging function is subsequently passed to the socket instances created by listen() and register().

This allows diagnostic information from the network layer to be centralized.

**Using the constructor without a debugging function**
`
``javascript
const node = new TelepathyMQ('server');
```

In this case, the constructor automatically uses an empty function:

```javascript
() => {}
```

No debugging output is therefore generated through this default function.

7. Managing remote relationships

The constructor also initializes the relations property with an empty object.

```javascript
this.relations = {};
```

This property is used to store relationships with remote nodes.

When a remote node registers, TelepathyMQ adds a reference to its emitter in this object.

For example, in the listen() method:

```javascript
sock.on('register', (identity, emitter) => {
  this.relations[identity] = emitter;
});
```

The register() method also uses this property:

```javascript
sock.register(identity, connectString, emitter => {
  this.relations[identity] = emitter;
});
```

The emit() and defer() methods subsequently use these relationships to communicate with remote nodes.

**Example**

```javascript
const server = new TelepathyMQ('server');
const client = new TelepathyMQ('client');

// Establish the connection
client.register('server', 'tcp://127.0.0.1:8060');

// Send an event after registration
client.on('register', identity => {
  client.emit(identity, 'message', {
    text: 'Hello server'
  });
});
```

The relations property is therefore the internal mechanism used to locate available communication destinations.

8. Managing deferred operations

The constructor also initializes the defers property.

```javascript
this.defers = {};
```

This property is used to store asynchronous remote operations created with defer().

Each operation receives a UUID that allows individual requests to be identified.

**Example**

```javascript
const client = new TelepathyMQ('client');

const operation = client.defer('server', 'calculate', {
  a: 10,
  b: 20
});

operation.progress(data => {
  console.log('Progress:', data);
});

operation.done(result => {
  console.log('Result:', result);
});

operation.fail(error => {
  console.error('Error:', error);
});
```

When an operation is created, TelepathyMQ stores its deferred object in this.defers.

This object allows the corresponding operation to be retrieved when a result, notification, or rejection is received.

Initializing this property ensures that each instance has its own storage for managing deferred operations.

9. Managing sockets

The constructor initializes the socks property with an empty array.

```javascript
this.socks = [];
```

This array contains the sockets created by the TelepathyMQ instance.

Sockets are added when calling listen() and register().

**Example using listen()**

```javascript
const server = new TelepathyMQ('server');

server.listen(8060);
```

**Example using register()**

```javascript
const client = new TelepathyMQ('client');

client.register('server', 'tcp://127.0.0.1:8060');
```

In both cases, the created socket is stored in this.socks.

This property subsequently allows the close() method to centrally close the connections managed by the instance.

```javascript
node.close(error => {
  if (error) {
    console.error(error);
    return;
  }

  console.log('Connections closed');
});
```

Each instance maintains its own socket array.

10. Complete example

The following example demonstrates how to create two TelepathyMQ nodes and use them to establish communication.

**Server**

```javascript
const TelepathyMQ = require('telepathymq');

const server = new TelepathyMQ('server');

server.on('register', identity => {
  console.log('Node connected:', identity);
});

server.on('unregister', identity => {
  console.log('Node disconnected:', identity);
});

server.on('message', data => {
  console.log('Message received:', data);
});

server.listen(8060, () => {
  console.log('Server listening on port 8060');
});
```

**Client**

```javascript
const TelepathyMQ = require('telepathymq');

const client = new TelepathyMQ('client');

client.on('register', identity => {
  console.log('Connected to:', identity);

  client.emit('server', 'message', {
    text: 'Hello from client'
  });
});

client.register('server', 'tcp://127.0.0.1:8060');
```

In this example:

- The server is created with the identity server.
- The client is created with the identity client.
- The server starts listening on port 8060.
- The client establishes a connection with the server.
- The client receives the register event.
- The client sends a message event to the server.
- The server receives and processes the message.

This example illustrates the constructor's role in creating the nodes that make up a TelepathyMQ architecture.

11. Best practices

- Assign an explicit and easily identifiable identity to each node.
- Use unique identities within the communication network.
- Provide a custom debugging function during development when necessary.
- Avoid directly sharing internal instance properties between multiple components.
- Use listen() to accept incoming connections.
- Use register() to establish connections with remote nodes.
- Register event listeners using on() before starting communication operations when necessary.
- Use defer() when the result of a remote operation is required.
- Use close() to close connections managed by the instance.
- Implement appropriate error handling for network operations and asynchronous communications.
- Avoid creating multiple instances with the same identity within the same communication environment unless an appropriate strategy has been defined.

13. Important considerations

**Node identity**

The identity is assigned directly when the instance is created.

It is used to identify the node within TelepathyMQ communications.

It is recommended to use explicit, stable, and unique identities within the network.

However, the constructor does not check whether the identity is valid or already in use.

**No automatic network connection**

Creating a TelepathyMQ instance does not start any network connection.

It only initializes the internal properties required by the node.

To make the node operational, the following methods must subsequently be used:

listen() to accept incoming connections.
register() to connect to a remote node.

This distinction is important: creating an instance and establishing a connection are two independent operations.

**Optional debugging function**

If no debugging function is provided, TelepathyMQ uses an empty function.

This means that applications are not required to implement a logging mechanism.

The provided function is passed to sockets created by the instance.

It is recommended to use a custom debugging function during development to make communication issues easier to diagnose.

**Isolation of internal properties**

Each instance has its own relations and defers objects, as well as its own socks array.

These properties allow connection management and deferred operations to remain isolated between different nodes.

It is preferable not to modify these properties directly from application code.

**EventEmitter inheritance**

TelepathyMQ inherits from EventEmitter, allowing it to use Node.js native event management features.

However, the emit() method is overridden to support communication with remote nodes.

It is therefore important to distinguish between listening for local and incoming events using on() and sending remote events using emit().

**No parameter validation**

The current constructor implementation does not explicitly validate its parameters.

In particular, it does not check:

- Whether identity is a string.
- Whether identity is empty.
- Whether the identity is unique within the network.
- Whether debugFunction is actually a function.

Adding these validations could help detect configuration errors as soon as an instance is created.

**Instance lifecycle**

A TelepathyMQ instance is designed to manage its own connections and asynchronous operations.

It is recommended to follow a clear lifecycle:

- Create the instance.
- Configure event listeners.
- Start listening or establish connections.
- Exchange events and execute remote operations.
- Close connections using close() when the instance is no longer needed.

This approach simplifies resource management and reduces the risk of forgotten connections.

**General recommendation**

The new TelepathyMQ(identity) constructor is the entry point for using the library.

It initializes all internal structures required for managing connections, events, and deferred operations.

For reliable TelepathyMQ usage, applications should assign an explicit identity to each instance, validate configuration parameters, and follow the connection lifecycle.

**Additional implementation recommendations**

After reviewing the current implementation, I would consider four possible improvements:

- Validate identity: ensure that the value is a non-empty string.

- Validate debugFunction: explicitly reject values that are not functions when provided.

- Document identity uniqueness: explain the implications of two nodes having the same identity.

- Preserve encapsulation: consider protecting internal properties such as relations, defers, and socks against direct modifications by applications.

Keep the EventEmitter inheritance, however, is a consistent architectural choice for TelepathyMQ's event-driven communication model.
